# 3D for premium websites: Three.js / React Three Fiber / Drei

Real-time WebGL is the most expensive thing you can put on a web page. Treat every
scene like a performance loan you must pay back in load time, battery, and jank.
Stack: [three](https://threejs.org) (WebGL renderer), [@react-three/fiber](https://docs.pmnd.rs)
(R3F — React renderer over three), [@react-three/drei](https://github.com/pmndrs/drei)
(ready-made helpers). This file covers when to pay that price, how to keep it low,
and what to ship instead when you shouldn't.

## When 3D is actually worth the cost

Reach for real-time 3D only when at least one of these is true:

1. **The user manipulates it.** Drag-to-rotate a product, orbit a configurator,
   parallax tied to cursor/device orientation. Passive rotation can be faked.
2. **Depth or lighting sells the product.** Jewelry, sneakers, furniture,
   architecture — materials under moving light are the whole point.
3. **One scene replaces many assets.** A configurator with 40 colorways beats
   40 pre-rendered videos once the variant count is high enough.
4. **It is the brand moment.** One hero scene per site, not per section.

Do NOT reach for 3D when the effect is decorative motion. A rotating gradient,
floating cards, scroll-linked reveals, glow, noise, grain: all of these are
cheaper and sharper as CSS transforms/filters or SVG/canvas 2D. A pre-rendered
looping video (WebM/MP4) of a 3D scene often looks *better* than live WebGL —
perfect antialiasing, zero GPU cost after decode — and should be your default
for anything the user cannot interact with. If you can screenshot it, don't
render it.

Rule of thumb: interactive → WebGL; animated-but-passive → video or CSS;
static-with-depth → layered images/CSS 3D transforms.

## GPU budgeting

The GPU bill has four currencies. Measure before optimizing: drop drei's
`<Stats />` next to your scene in dev, and read `state.gl.info.render.calls`,
`state.gl.info.render.triangles`, and `state.gl.info.memory.textures` inside
`useFrame` or via the stats panel.

**Draw calls** — one per mesh × material × light interaction pass; the CPU-side
cost dominates on weak phones. Budget roughly: desktop hero ≤ ~150 calls total
page-wide, mobile ≤ ~50. Tactics:

- Merge static geometry into few meshes (BufferGeometryUtils.mergeGeometries).
- Repeated objects (dots, confetti, grid items): `THREE.InstancedMesh`, or drei's
  `<Instances>`/`<Instance>` — thousands of copies, one call.
- Lights: 1 directional + ambient + environment map beats 4 point lights. Bake
  shadows for static scenes (`BakeShadows`) instead of real shadow maps.
- Multiple canvases on one page multiply everything. Use drei's `<View>` to
  share a single canvas across several viewport-tracked regions if needed.

**Triangles** — desktop hero scenes comfortably run 100k–500k tris; keep mobile
under ~100k. Decimate source meshes, delete hidden faces, and ship glTF with
Draco or Meshopt compression (draco-transformer / gltfpack at build time).

**Textures** — VRAM = width × height × bytes-per-pixel, so a 2048² uncompressed
RGBA texture is ~16 MB. Rules:

- Power-of-two dimensions, always mipmapped.
- Compress: KTX2/Basis Universal via `KTX2Loader` — same quality at a fraction
  of VRAM and bandwidth versus PNG/JPEG.
- Hero PBR set at 1024–2048 on desktop; 1024 max on mobile; skip normal maps
  below ~300 px screen size.
- Set `texture.colorSpace = THREE.SRGBColorSpace` on color maps only.

**Fill rate / pixels** — cap the device pixel ratio:
`<Canvas dpr={[1, 2]} />` (never raw `devicePixelRatio`, which is 3+ on many
phones). Full-screen postprocessing (bloom, DOF) multiplies fragment cost —
desktop only, and prefer cheap passes. Particle counts: `THREE.Points` with a
custom shader material handles 50k–200k points in one draw call; never make a
particle a separate mesh. 10k individual sprites is already a mistake.

## Mobile fallback strategy

Detect capability up front, before any 3D code loads:

```js
function webglOk() {
  try {
    const c = document.createElement('canvas')
    return !!(c.getContext('webgl2') || c.getContext('webgl'))
  } catch { return false }
}
```

Layer the decision:

- **No WebGL** (old devices, locked-down browsers): static image or video of
  the scene. Never show a black rectangle — bake a frame from your scene
  (`canvas.toDataURL` in dev, or a designer render).
- **Constrained hardware**: `navigator.hardwareConcurrency <= 4`,
  `navigator.deviceMemory <= 4` (Chromium-only; treat as a hint), coarse
  pointer, or `matchMedia('(prefers-reduced-motion: reduce)')` matching.
  Ship the same scene degraded: lower `dpr` floor, no shadows/postprocessing,
  halved particle counts, simpler LOD via drei's `<Detailed distances={[0, 8, 16]}>`.
- **Respect reduced-motion even on fast machines**: pause autorotation and
  scroll-driven camera moves; render one frame (`frameloop="demand"`).

R3F gives you runtime degradation for free-ish: wrap the scene in
`<PerformanceMonitor onDecline={...}>` (or `<AdaptiveDpr pixelated />`) so FPS
drops step the resolution down instead of stuttering.

## Lazy-loading the 3D scene

Never let the 3D bundle touch the critical path. The whole `three` +
`@react-three/fiber` graph lives behind a dynamic import:

```jsx
// Hero.jsx — ships without any three.js code
import { Suspense, lazy } from 'react'

const Scene = lazy(() => import('./Scene')) // contains Canvas + three

export function Hero({ enable3d }) {
  if (!enable3d) return <FallbackImage />
  return (
    <div ref={containerRef} /* mount gate via IntersectionObserver */>
      <Suspense fallback={<FallbackImage />}>
        <Scene />
      </Suspense>
    </div>
  )
}
```

Details that matter:

- Gate mounting on `IntersectionObserver` so a below-the-fold canvas never
  initializes until near the viewport; unmount/pause it when far off-screen.
- In Next.js, `dynamic(() => import('./Scene'), { ssr: false })` — R3F needs
  the DOM and will crash SSR otherwise.
- Inside the Canvas use `<Suspense>` around async assets (`useGLTF`,
  `useTexture`) and drei's `<Preload all />` to warm them; surface progress
  with `useProgress` for a loader UI.
- Mostly-static scene? `frameloop="demand"` renders only when `invalidate()`
  is called — near-zero idle GPU/battery cost. Switch back to `'always'` while
  animating.
- Pause work when the tab is hidden: rAF throttles automatically, but stop
  your own timers/intervals and consider `document.visibilitychange` to drop
  to `frameloop="demand"`.

## Choosing per section: asset vs procedural vs shader vs image

For each section, answer in order:

1. **Does it move or respond at all?** No → plain image (AVIF/WebP), done.
   A `<picture>` with art direction beats everything on cost.
2. **Is it passive motion?** → looping video or CSS animation. Not WebGL.
3. **Simple geometry + light response?** (gradient blobs, wobbly shapes,
   distorted planes) → procedural geometry built in code (spheres, tori,
   planes with vertex displacement) plus a custom shader via drei's
   `shaderMaterial()` + `extend`. Zero download cost beyond the bundle.
4. **Recognizable object, brand-critical?** → real modeled asset: glTF with
   Draco/Meshopt + KTX2 textures, loaded with `useGLTF`. Only here does an
   artist pipeline earn its keep. Keep first-load payload (geometry +
   textures) under ~1–2 MB compressed.
5. **Thousands of tiny things?** → procedural + instancing (`<Instances>`,
   `THREE.Points`). Never model them individually.
6. **Full-screen atmosphere (grain, glow, fluid)?** → fragment shader on a
   fullscreen quad, not particles or geometry.

Final pre-ship checklist:

- [ ] Interaction or depth genuinely required? (else: image/video/CSS)
- [ ] Draw calls ≤ target for tier; verified with `<Stats />`
- [ ] Textures KTX2-compressed, pow2, mipmapped, correct colorSpace
- [ ] Geometry Draco/Meshopt-compressed; triangle count within budget
- [ ] `dpr` capped; shadows/postprocessing disabled on constrained tiers
- [ ] Static fallback (image/video) for no-WebGL and reduced-motion users
- [ ] Scene dynamically imported, gated on viewport visibility
- [ ] `frameloop="demand"` or paused when idle/hidden
